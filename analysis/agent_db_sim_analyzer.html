Agent–DB Workload Analyzer

Closed-loop statistical model of N agents cycling think → LLM call → DB query. Analytic engine: exact Gordon–Newell/Buzen closed-chain means (exact at SCV=1, cross-checked vs. CTMC) plus calibrated latency percentiles. Monte Carlo engine: exact FCFS discrete-event simulation. See the assumptions panel for model math & references; the repo's DES simulator is documented separately in the root README.

How to read this page

  1. Every parameter on the left plugs into exactly one box of the loop above (think time on the arrow, τ/c/SCV inside its endpoint).
  2. The engines compute what steady state looks like: tiles = the headline numbers, charts = the distributions, table = per-endpoint detail.
  3. Use Monte Carlo / Compare to check the analytic estimates with a discrete-event simulation.

Agents

How many agents run the loop at the same time. More agents = more load on both endpoints; this is the main "demand" dial against the fixed server capacities.
The non-work time between an agent finishing one loop and starting the next. Long think time spreads agents out, lowering pressure. N × (1/τthink) roughly bounds how much load the agents can generate.

Topology — station chain

Agents visit every listed station once per cycle, in order — each row is an M/G/c endpoint (parallel servers, service jitter). Model multiple compute and storage nodes by chaining them (preset 2), or extra inference stages by adding a second LLM-class station. Rescan: the first row is entered first.

What the tiles mean
tileplain meaning
p50 / p90 / p95 / p99Percentiles of the whole loop time (think + call + query + all waiting): p95 = 95% of cycles finish within this time. The gap between p50 and p99 tells you how spiky the agent experience is.
mean ± sdAverage loop time and its natural spread.
throughput XCompleted loops per second across the whole system. Also = the arrival rate into every endpoint (each loop hits each box exactly once — that's why one X feeds all stations).
ρ LLM / DBPer-server load at each endpoint = fraction of time a typical server is busy. ρ→1 means saturation: each extra agent adds queues faster than work finishes.
P(wait) LLM/DBChance that a freshly arriving call/query finds all servers busy and must queue. High P(wait) with moderate ρ usually means too little capacity headroom or too much service jitter.

Agent cycle-latency distribution

think + LLM sojourn + DB sojourn · PDF (area) and CDF with percentile markers.

How to read: the x-axis is the total wall-clock time of one full loop. The shaded area (PDF) shows which latencies are common — its height is “how much probability mass sits here”. The rising line (CDF) reads “the share of loops completing within x seconds”. The dotted verticals mark p50/p90/p95/p99 on that CDF. A long right tail = occasional agents stuck behind big queues; a narrow bump = stable, well-provisioned system.

Arrival occupancy at the DB

Exactly how many agents were already there when an agent arrives to add its query (arrival theorem, N−1 chain).

How to read: each bar is the exact probability that an arriving query joins n other agents already at this endpoint — the DES traces would measure the same empirical histogram. Mass sitting at 0 = arriving to an empty endpoint (no queue to join); the tail beyond the server count is the fraction of arrivals that must wait. Heading over the bars shows the mean seen.

Saturation sweep — mean cycle latency vs. agent count

Analytic engine · knee (steepest slope) and near-saturated points marked.

How to read: each point answers “what happens to everyone's loop time if we run this many agents”. Flat start = spare capacity; the warn-dot knee = the agent count where latency starts growing fastest (plan capacity below this); red verticals = counts where an endpoint is ≥99.5% busy and loop time is running away. Horizontal distance between your current N and the knee is your headroom.

Per-station breakdown

Column meanings
  • λ = X — arrival (= completion) rate at that endpoint, loops/s; identical for every endpoint by flow balance.
  • ρ/server — per-server busy fraction; the bottleneck is the row closest to 1.
  • P(wait>0) — how often arrivals find the endpoint busy.
  • Wq — average pure waiting time in that queue (this is the amount you can shave by adding servers).
  • R = τ+Wq — total time one call/query spends inside the endpoint (wait + service).
  • Lq — average number of agents standing in that queue right now.
Bottleneck rule of thumb: the row with max ρ gates the whole loop — adding capacity anywhere else helps much less.
Model assumptions, math & references
  • Closed loop: each of N agents runs think → LLM → DB sequentially; think time exponential (memoryless); service times general via SCV (c²ₛ = Var/Mean²).
  • Analytic means (exact at SCV=1): product-form closed network — Gordon & Newell, Oper. Res. 15(2), 1967; multiserver FCFS valid via the BCMP theorem, JACM 22(2), 1975 — solved exactly by Buzen's convolution (Comm. ACM 16(9), 1973); sojourns via Little's Law (Little, Oper. Res. 9(3), 1961), R = L/X.
  • M/G/c (SCV≠1): mean wait inflated by the Allen–Cunneen factor (c²ₐ+c²ₛ)/2 with c²ₐ=1 — Kingman-type (1961) approximation; see Whitt, "The Queueing Network Analyzer", BSTJ 62(9), 1983.
  • Latency percentiles: wait modelled as P(W=0) = 1−π̂ else Exp(μ̂) — in the closed chain a waiting agent sees all c servers busy, so the tail rate is μ̂=c/τ (empirically chosen vs Monte Carlo); π̂ = μ̂·W rescaled to reproduce the exact chain mean wait. Phases (Exp(think) ⊛ wait mixtures, shifted by constant services T₀) convolved numerically on a uniform grid → CDF → percentiles. Expect ±10–15% agreement with the MC tab; switch to MC for empirical percentiles.
  • Monte Carlo: exact FCFS discrete-event simulation (event list in time order, FIFO queues, per-server busy counts); Gamma service sampling (Marsaglia & Tsang, ACM TOMS 26(3), 2000); percentiles over warm-up-trimmed completed cycles; error O(1/√n).
  • Near-saturation: closed chains are stable for finite N (ρ<1); ρ≥0.995 is flagged and the sweep shows rapid growth.
  • General references: Bolch et al., Queueing Networks and Markov Chains, Wiley 2006 · Lazowska et al., Quantitative System Performance, 1984. Verified against a brute-force CTMC stationary solve (see analysis/verify_core.js).
